# 01 · 问题清单与证据

每个问题都标了「在哪看到的 / 代价 / 对应任务」。行号基于 v0.6.0 快照（`source/find-fast-v0.6.0/`），改动后会有偏移，用函数名搜索。

## 总判断

「秒搜文件」的定位是**瞬时唤起、输两个字母、回车打开**。但它的结果区是**管理后台表格**：五个列、可拖动列头、每行末尾一个定位按钮、操作按钮在上方另起一条。用户在做的事只有两件——「在几十条候选里认出我要的那条」和「打开它」。界面上有一半元素在为这两件事之外的目的服务。

---

## P1 · 直接拖慢主任务

### 1. 结果里没有任何命中高亮

**证据**：`find_fast.html:700 renderRow()` 用 `textContent` 写入 `r.name`；`find_fast_gtk.py:1642 fill()` 往 Store 里塞 `core.display(name)`，cell 只绑定 `text`。全仓库搜索 `<mark`、`background=` 无命中。`core.match_positions()`（`find_fast_core.py`）返回的是**匹配条目的编号**，不是字符位置，从来没有被界面用来做高亮。

**代价**：用户输入「报告」，得到 40 条含「报告」的文件名，得自己逐字扫描定位。这是每次搜索都要付的成本。

**任务**：T02

### 2. 最宽的一列给了重复信息

**证据**：`find_fast_gtk.py:804` 给 `path` 列 `set_expand(True)`，路径吃掉全部剩余宽度；`find_fast.html:31` 的表格里路径列同理。而实测连续 8 行的路径都是 `/root/proxy/data/logs`——同一目录下的文件，路径完全重复。

**代价**：真正需要区分的文件名被挤到最小宽度。760px 窗口下实测文件名换行成两截：`service.2026-1` / `17.user.1.log`。

**任务**：T03

### 3. 操作按钮离选中的行很远，且混了全局动作

**证据**：`find_fast.html:151` 的 `.actions` 在表格**上方**，四个按钮：打开 / 定位 / 复制路径 / 重新扫描；前三个在未选中时 `disabled`（`select()` 里 `$(id).disabled = cur < 0`）。GTK 侧没有按钮，全靠右键菜单，两平台行为不一致。

**代价**：视线在「上方按钮」与「列表中的选中行」之间往返；`重新扫描` 与选中无关，却和选区动作排在一起，误点代价高（大索引重扫几十秒）。

**任务**：T04

### 4. 没有结果时没有出口

**证据**：`find_fast.html` 里根本没有空状态元素——搜索无结果时 `<tbody>` 为空，只剩一行表头，状态栏显示「0 个结果」。GTK 侧只有 `find_fast_gtk.py:830` 一句 `no_match` 的 dim label，居中浮在空白上。

**代价**：用户不知道是「没这个文件」还是「搜索词写错了」还是「索引还没建好」。零结果是最需要引导的状态，却是信息最少的状态。

**任务**：T07

## P2 · 增加噪音与认知负担

### 5. 语法帮助是一段常驻的百字长文

**证据**：`find_fast.html:150` `<p class="help" id="help">`，文案在 `T.zh.help`，约 100 字，永远占一行到两行高度。GTK 侧靠占位符文本塞同类提示。

**代价**：95% 的时间用户不看它，但它每天都在挤占结果区高度；真正需要时又读不进去（一段纯文本，无结构）。

**任务**：T08

### 6. 状态信息在两处重复

**证据**：`find_fast.html:157` 的 `#status` 报「N 个结果」，页脚 `#index` 又报「共 N 个条目 / 实时更新」。GTK 侧 `self.status` 与 `self.state` 两个 label 分列左右。

**代价**：两个数字长得像但含义不同（结果数 vs 索引条目数），并排出现时用户会误读。

**任务**：T05

### 7. 半屏使用必须横向滚动

**证据**：`find_fast.html:31` `table { min-width: 560px }`。快捷键唤起的窗口常见宽度是 600–900px，减去 padding 与滚动条后在 560px 边界附近反复横跳。

**代价**：出现横向滚动条时，表格的「修改时间」列被切掉，而它是排序依据。

**任务**：T03、T11

### 8. 折叠态会把搜索框一起裁掉

**证据**：`find_fast_gtk.py:1383 apply_layout()` 里 `self.win.resize(self.size[0], self.size[1] if want else 1)`——收起时窗口高度设成 **1px**，靠 WM 的最小高度约束兜底。不同 WM 的最小高度不同，实测在部分环境下搜索框下半截被裁。

**代价**：收起状态是「随时待命」状态，视觉残缺会让人以为程序坏了。

**任务**：T10

### 9. 设置对话框是一条长列表

**证据**：`find_fast.html:181` 起，`#settings` 里依次是根目录、排除、两个复选、列顺序、恢复默认、取消/保存，全部纵排。GTK 侧 `find_fast_gtk.py:1032 open_settings()` 同样是单页堆叠，还塞进了升级与唤起键。

**代价**：找「索引隐藏文件」这种开关要滚；「列顺序」这种一次性配置与高频配置混在一起。

**任务**：T09

### 10. 用 emoji 当类型图标

**证据**：`find_fast.html:710` `kind.textContent = r.folder ? '📁' : ''`。

**代价**：`📁` 在部分发行版/字体缺失时渲染成方框或彩色 emoji，与 12px 的行内文字基线对不齐；GTK 侧用主题图标名，两侧视觉不一致。

**任务**：T03

## P3 · 结构性缺失

### 11. 结果多时没有收敛手段

**证据**：界面只有排序（`#sort` 七个选项），没有任何缩小范围的入口。搜 `jpg` 出来几千条时，唯一动作是滚动。

**代价**：大结果集等于不可用。用户被迫改搜索词，回到输入端重来。

**任务**：T06

### 12. 键盘只能上下移动，不能直达

**证据**：`find_fast.html:733 select()` 只处理方向键；没有 Home/End、没有 PageUp/PageDown、没有「跳到第 N 条」、没有类型快捷键。GTK 侧稍好（`on_tree_key`），但仍无分页跳转。

**代价**：40 条结果里选第 30 条要按 30 次 ↓。

**任务**：T08

## 已确认**不是**问题的部分（别改）

| 项 | 原因 |
|---|---|
| 搜索语法本身 | 多词 AND、词可落路径、`a\|b`、`!`、`*?`、`ext:`、`path:`、`regex:` 已经够用，语义清晰，改它只会打破用户肌肉记忆 |
| 类似版本标签 | 「最新 / 有更新版」是差异化功能，保留原样 |
| 增量监听与扫描 | 索引层不要碰 |
| 升级 / 回退链路 | 与交互无关，且带签名校验，改它风险远大于收益 |
| 唤起键与 `--toggle` | 不动 |
