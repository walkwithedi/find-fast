# T12 · 性能与虚拟化

**状态**：待做　**优先级**：P2　**平台**：双　**依赖**：T03、T06　**预估**：1 人日

## 目标

10 万结果下滚动 ≥50fps，输入到出结果 ≤120ms，内存 <80MB。两行结构 + 高亮不能把原来的流畅度吃掉。

## 预算

| 指标 | 目标 |
|---|---|
| 输入 → 首屏结果 | ≤120ms（10 次中位） |
| 选中切换 | ≤16ms（只改两行） |
| 滚动（10 万结果） | ≥50fps |
| 首屏 200 行渲染 | ≤50ms |
| GTK `fill()` 单次 | ≤8ms |
| 页面内存 | <80MB |

## 必做项

### Web

1. 渲染分批：首屏 200 行，滚动到距底 20 行追加；用 `DocumentFragment` 一次插入（不要逐行 `appendChild` 触发 200 次重排）。
2. 选中只改两行：`paintSel(prev, next)` 只 toggle 两个元素。
3. 高亮只在服务端对返回行算（T02 已如此）；前端不做二次解析。
4. 输入防抖 120ms + `AbortController` + `seq` 丢弃乱序响应。
5. 筛选条只在计数变化时重绘（用签名字符串比较：`facets.join()`）。
6. 滚动回调 `requestAnimationFrame` 节流；批量读后批量写。

### GTK

1. 保持「Store 只装可见行」：`fill()` 的复杂度是 O(可见行数)，不要改成全量 model。
2. `measure_row_height()` 常量 48，不再 `cell_get_size()`。
3. `fill()` 里避免每行 `GLib.markup_escape_text` 多次调用同一字符串；`human_size` 结果相同的行可复用。
4. `on_adj` / `scroll_to` 用 `GLib.idle_add` 合并，一次滚动只 `fill()` 一次。
5. 高亮色按主题缓存到 `self.mark_bg / self.mark_fg`。

## 测量方法

```js
// 输入到上屏
const t0 = performance.now();
await searchNow();

```


## 风险

- `innerHTML` 批量赋值比逐行 `appendChild` 快，但会丢事件监听——本项目用事件委托，可以用。
- 如果 `facets` 同步计算拖慢首屏，改为 `facets: null` + 二次请求（T06 已给方案）。
- GTK 的 Pango markup 解析比纯文本贵约 3 倍；若 `fill()` 超 8ms，退化为「只对名称行加 markup，路径行纯文本 + 整段高亮背景」。
