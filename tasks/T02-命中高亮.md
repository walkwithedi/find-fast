# T02 · 命中高亮

**状态**：完成　**优先级**：P0　**平台**：双（core 共享）　**依赖**：T01　**预估**：1.5 人日

## 目标

搜索结果里，用户输入的词在**文件名**和**路径**中的每一次出现都带暖黄底，让「一眼认出目标」变成可能，而不是逐字扫描。

## 为什么

v0.6.0 两侧都只渲染纯文本（`renderRow()` 用 `textContent`，GTK 用 `text` 属性）。`core.match_positions()` 返回的是条目编号，不是字符位置，从未用于高亮。用户每次搜索都要自己找。

## 改动点

| 文件 | 改什么 |
|---|---|
| `find_fast_core.py` | 新增 `highlight(text, clauses, mode, mark_bg, mark_fg)`、`highlight_row(name, dir_display, clauses)`、`_escape_html()`、`_escape_pango()` |
| `find_fast_web.py` | `/api/search` 返回 `name_html`、`dir_html`、`dir_display`；`clauses` 存进 holder 复用 |
| `find_fast.html` | `renderRow()` 用 `innerHTML` 渲染这两段；缺字段时退回 `textContent` |
| `find_fast_gtk.py` | `fill()` 生成 `values[7]`（名称+路径 markup）与 `values[8]`（元信息） |
| `tests/test_highlight.py` | 已有 12 条用例，实现后全绿 |

## 函数契约

见 `docs/06` 6.1 的 `highlight()`，11 条规则必须逐条满足。摘要：

- 只标正向词；`!词` 不标。
- 子串匹配大小写不敏感、标**全部**出现；wildcard 用正则 `finditer`；`ext:` 标后缀。
- 区间合并、按起点排序、最多 24 段。
- **先转义再插标记**；`html` 模式用 `<mark>`，`pango` 模式用 `<span background=…>`。
- 空查询/空文本返回转义原文。

## 实现要点

1. Web 侧只对本次返回的行算（`limit` ≤500），不要预计算全量。
2. `dir_html` 基于 `core.short_dir(folder)` 的**输出串**计算，不是原始路径——否则区间会整体错位。
3. 名称里已标到的词，不再在路径里重复标（`highlight_row` 负责去重），避免一行里出现两处同样的黄块。
4. GTK 的 `mark_bg` 按主题：浅色 `#ffe9a8`，深色 `#3a3320`；`mark_fg` 深色 `#ffd98a`，浅色不设（继承）。
5. 选中行的高亮底不变，但 GTK 需确保 `foreground` 不被主题的选中色覆盖——显式写 `foreground`。
6. 性能：单行 <0.1ms，200 行 <20ms。若超过，先查是否每行都重新 `parse_query`（应复用 `clauses`）。

## 风险

- Pango markup 里 `<`、`&`、`'`、`"` 必须转义，否则**整行不渲染**且不报错——这是 GTK 侧最常见的「空白行」原因。
- Python 用码点、JS 用 UTF-16：**不要**把区间传给前端，一定传渲染好的字符串（这是本任务的核心决策）。
- `regex:` 模式的零宽匹配（如 `a*`）会死循环，`finditer` 时跳过 `start == end`。

T02 采用开发包高亮参考实现；查询解析每次搜索仅运行一次。
